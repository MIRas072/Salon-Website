# Система управления салоном — версия 2

Статус: код и локальная проверка готовы. Рабочий сайт пока использует прежнюю версию. Переключать публичную запись на V2 можно только после серверного подключения Firebase, миграции и проверки на отдельном адресе.

## Состав

- `next/`: клиентский сайт, кабинет, политика данных, самостоятельная отмена. Vanilla JavaScript, адаптивная вёрстка, без обязательного платного UI-сервиса.
- `backend/`: Node.js API, проверка данных и ролей, транзакции, очередь писем, резервные копии и миграция.
- Production: Netlify Functions + Firebase Authentication + Cloud Firestore. Для разработки: Node.js + SQLite. SQLite-файл нельзя использовать как постоянную базу в Netlify Functions.
- `netlify.toml` и `scripts/build.cjs`: сборка по списку разрешённых публичных файлов. Ключи, локальная база, резервные копии и серверные исходники в публичную папку не попадают.

Версия для одного салона. Для другого заказчика нужны отдельные Firebase-проект, Netlify-проект и аккаунт владельца. Это не общий многопользовательский SaaS.

## Возможности

Услуги, цены и длительности редактируются в кабинете; мастер выбирает услуги. Недельный график и смены на конкретную дату поддерживают несколько интервалов и выходной. При изменении конкретной смены сервер запрещает оставить активные записи за её пределами. Изменение недельного шаблона не переносит уже созданные записи: проверьте их отдельно. Длительность и цена сохраняются в записи; новые значения каталога применяются к новым записям и изменению услуги.

Сервер проверяет настоящий календарный день, часовой пояс, период записи, время до визита, совместимость мастера и услуги, рабочую смену и полный интервал услуги. Каждые 30 минут резервируются атомарно. Версия записи защищает от потери изменений двух администраторов. Повтор запроса с тем же ID не создаёт вторую запись/оплату.

Новая заявка держит время 4 часа по умолчанию. Подтверждение сохраняет бронь; отмена освобождает все окна. Истёкшая заявка хранится в истории, но её окна больше не блокируют запись. Проверка срока происходит при чтении и резервировании, без обязательного платного планировщика Firebase.

Ссылка отмены использует случайный секрет в URL-фрагменте, в базе хранится только его SHA-256. После открытия фрагмент удаляется из адресной строки. Клиенту нужно сохранить исходную ссылку. Повтор запроса создания подтверждает результат, но не возвращает секрет отмены снова; при потере ответа клиент связывается с салоном.

Клиенты объединяются по нормализованному телефону; доступны заметки и история до 100 визитов. Есть записи оплат/возвратов (наличные, карта, перевод), суммы по загруженным записям, журнал действий и экспорт JSON. Это внутренний учёт, а не эквайринг или фискальная касса. Старые записи не удаляются необратимо из кабинета: для исключения используется отмена. Владелец может удалить личные данные клиента из закрытой истории: имя, телефон, почту и комментарии, сохранив обезличенный финансовый учёт. Активные записи сначала нужно завершить или отменить. Старые коллекции и ранее сохранённые копии требуют отдельной обработки. Сроки хранения должны быть согласованы владельцем.

## Запуск без production-ключей

Нужен Node.js 22.13+ (проверено на 24). Из корня:

```sh
npm ci --cache /tmp/salon-npm-cache
npm test
npm run build
npm run dev
```

Сервер слушает только loopback, порт 8030 по умолчанию (`PORT` меняет порт). `/api/v2/health` возвращает `{ok:true,version:2}`. Сайт находится в `/next/index.html`, кабинет — `/next/admin.html`. Локальный вход открывает исключительно тестовую SQLite-базу `.local/salon.sqlite`. Он недоступен в production-функции. Не публикуйте dev-сервер и не используйте локальный вход с настоящими клиентскими данными.

```sh
npm run test:ui
```

Браузерный тест сам создаёт отдельную временную базу и сервер, затем удаляет их. Playwright закреплён в devDependencies. Используется `/usr/bin/chromium`, `CHROMIUM_PATH` или установленный браузер Playwright (`npx playwright install chromium`). Это инструменты разработки, а не зависимости опубликованного сайта.

20 тестов SQLite покрывают гонки, перемещение часа, отмену, срок заявки, серверную валидацию, роли, лимиты, оплаты, экспорт/восстановление, миграцию и отключённые уведомления. 17 основных тестов также прошли на официальном эмуляторе Firestore. Эмулятор не проверяет наличие production-индексов. UI-тест прошёл запись, подтверждение, перенос, оплату, заметки, конфликт смены, отмену, экспорт и ширины 390/320px. Вход через настоящую Firebase Authentication и публикация Netlify Functions требуют отдельной проверки после настройки.

## Серверное подключение

В Netlify Project configuration → Environment variables задайте серверные переменные:

- `FIREBASE_SERVICE_ACCOUNT`: JSON отдельного Firebase service account. Ключ берётся в Firebase Project settings → Service accounts → Generate new private key. Не отправляйте файл/значение в чат, не помещайте в `firebase-config.js`, Git или папку сайта. Для долгой эксплуатации предпочтителен механизм идентификации без долгоживущего ключа, если платформа его поддерживает.
- `FIREBASE_PROJECT_ID`: `salon-11-9ddab` для текущего салона.
- `SALON_OWNER_EMAIL`: почта владельца.
- `SALON_OWNER_UID`: UID владельца из Firebase Authentication, если его почта не подтверждена. Иначе владелец должен подтвердить почту; одного совпадения неподтверждённой почты недостаточно.
- `SITE_URL`: публичный адрес сайта.

Ключ должен относиться именно к этому проекту и иметь минимальные необходимые права Firestore и Firebase Authentication для проверки отозванных сессий. Для создания индексов отдельно нужен доступ администратора проекта. Веб-конфигурация Firebase остаётся публичной.

Production использует коллекции `salonV2`, `bookingsV2`, `availabilityV2`, `customersV2`, `membersV2`, `auditV2`, `rateLimitsV2`, `requestsV2`, `notificationsV2`. Доступ к ним из браузера должен быть запрещён: API работает через серверный SDK. Нынешнее завершающее правило `allow read, write: if false` уже закрывает эти новые коллекции. **Не заменяйте действующие правила файлом `firestore-v2.rules`, пока работает старый сайт:** это отключит прежнюю запись. Файл V2 — закрытая политика для отдельного проекта/полного перехода.

Создайте необходимые индексы из `firestore.indexes.json` через консоль Firebase или официальный CLI с доступом к проекту. После этого публикуйте сначала отдельную preview-версию сборки, не заменяя основной сайт. Netlify должен собирать проект (`npm run build`), а не получать только папку HTML через Drop: серверные функции должны быть собраны и развёрнуты вместе с сайтом.

## Доступы и подготовка к работе

Владелец может добавлять UID сотрудников с ролями управляющего, администратора и мастера. Управляющий редактирует настройки и читает журнал; администратор ведёт записи/клиентов; мастер читает только свои записи и отмечает завершение. Только владелец управляет доступами и скачивает полную копию.

В кабинете проверьте длительности **каждой** услуги. По умолчанию сохраняются старые значения: окрашивание в один тон 60 минут, остальные 30. Это не утверждённая технологическая карта процедур. Владелец должен установить реальные смены/перерывы, контакты и политику обработки данных. Онлайн-запись закрыта до утверждения политики. Шаблон политики не заменяет согласованный юридический документ; отдельно проверьте требования к размещению данных в выбранном регионе Firestore.

## Перенос старых записей

1. Выделите время перехода и временно остановите старую запись. Старые и новые коллекции не синхронизируются: нельзя вести параллельно две независимые системы записи для одного салона.
2. С серверным доступом выполните dry-run. Укажите `LEGACY_BACKUP_PATH` вне Git/публичной папки:

```sh
LEGACY_BACKUP_PATH=/private/legacy-before-migration.json node scripts/migrate-legacy.cjs
```

3. Скрипт создаёт закрытую копию, проверяет данные и конфликты. Файл уже существующей копии не перезаписывается. При конфликтах сначала разберите исходные записи. При повторном dry-run используйте новый путь копии.
4. Для применения нужен явный `--apply` и `MIGRATION_EXPECT_PROJECT`, совпадающий с целевым проектом. Импорт разрешён только в пустые коллекции V2. Небольшой импорт применяется одной транзакцией; предел — суммарно 300 записей и слотов, выше нужен отдельный инструмент пакетной миграции. Старые коллекции не изменяются.
5. Старые 30-минутные записи на окрашивание не расширяются автоматически. Список `needsDurationReview` требует ручной проверки соседнего времени. Старые неподтверждённые заявки после импорта нужно разобрать вручную.
6. Проверьте количество записей, мастеров, длительности и занятость; проведите контролируемую запись/перенос/отмену. Только затем переключите основной сайт и уберите старые страницы/прямой доступ записи. Правила старых коллекций после перехода должны закрыть клиентскую запись, сохранив согласованный доступ к архиву.

## Защита и уведомления

Сервер ограничивает публичные заявки: 10 в сутки с одного IP и 5 на один телефон. Обновление лимита — по UTC. Общий IP салона/оператора может затронуть нескольких людей; ручные записи сотрудника не ограничиваются этим лимитом. Это уменьшает спам, но не подтверждает владение телефоном. Дополнительная защита — Cloudflare Turnstile: задайте секрет `TURNSTILE_SECRET_KEY`, публичный `turnstileSiteKey` в настройках, правильный hostname и action `booking`. При её включении проверьте доступность внешнего сервиса и отказ при ошибке проверки.

Без сервиса доставки автоматические письма отключены. Кабинет обновляет выбранный период раз в минуту, уведомляет о новых заявках в этом периоде. Кнопка «Новые заявки за все даты» открывает отдельную очередь ожидающих подтверждения заявок независимо от периода; для длинного архива используйте фильтр дат и страницы по 100 записей. Браузерная вкладка не заменяет push-уведомления при закрытом кабинете.

Опциональная доставка через Resend: `RESEND_API_KEY`, подтверждённый `MAIL_FROM`, `ADMIN_NOTIFICATION_EMAIL`, `SITE_URL`. Появляются письма о новых заявках администратору и напоминания клиенту, если он указал почту и запись подтверждена. Netlify scheduled function проверяет очередь каждые 15 минут. Используются ID повторной отправки поставщика, пять попыток, проверка актуальной записи; перенесённые/отменённые напоминания отбрасываются. Это доставка с возможными задержками и ограничениями провайдера, не гарантия получения письма. Реальная доставка в этой задаче не подключалась и не проверялась. Автоматические WhatsApp/SMS требуют отдельной интеграции с официальным провайдером; существующий WhatsApp — ручная связь.

## Копии, расходы и эксплуатация

Экспорт кабинета содержит данные и хеши секретов отмены, но не серверный ключ или пароли Firebase. Восстановление проверено в **пустую локальную SQLite-базу**:

```sh
npm run backup -- export /private/salon-backup.json
SALON_LOCAL_DB=/private/restored.sqlite npm run backup -- restore /private/salon-backup.json
```

Серверный инструмент также поддерживает Firestore: `SALON_BACKUP_TARGET=firebase npm run backup -- export /private/cloud.json`. Для восстановления используйте отдельный пустой Firebase-проект с его серверным ключом и `SALON_BACKUP_TARGET=firebase RESTORE_EXPECT_PROJECT=<project-id> npm run backup -- restore /private/cloud.json`. Предел восстановления одной транзакцией — 450 документов; большая база требует пакетного инструмента. Уже существующие V2-данные не перезаписываются. Этот код проверен на эмуляторе, восстановление настоящего production-проекта и автоматическое сохранение копий во внешнее закрытое хранилище ещё не настроены. Для продажи с обещанием восстановления нужен отдельный регламент и практическая проверка в отдельном Firebase-проекте. Без `SALON_BACKUP_TARGET=firebase` команда работает только с локальной SQLite-базой.

Платная подписка/биллинг в этой задаче не подключались. Netlify Functions и Firestore используют квоты действующих тарифов: бесплатный тариф не означает отсутствие лимитов. Просмотр расписания читает до 48 слотов и связанные занятые записи; кабинет загружает только период/страницу. Настройте наблюдение за квотами и доступностью сайта, проверяйте предупреждения Firebase/Netlify, не обещайте заказчику неограниченную работу. Сроки хранения архива, очистка служебных rate/request/outbox документов, автоматические копии, production-восстановление и оповещение о сбоях требуют отдельной настройки до обещания полного сопровождения.
